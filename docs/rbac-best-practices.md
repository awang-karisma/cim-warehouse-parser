# RBAC best practices and permission verbs in Go

**Recommendation for warehouse-parser:** Keep the typed `resource:action` catalog and use `create`, `read`, `update`, and `delete` for ordinary resource operations. Use a domain verb when a task deserves an independent grant or when CRUD would misdescribe the authority. Do not rename working permission keys just to match another project's vocabulary.

## What is standardized?

- **RBAC standardizes relationships, not a list of action names.** [INCITS 359:2012 (R2022)](https://shop.standards.ie/en-ie/standards/incits-359-2012-r2022--615043_saig_iti_iti_3389597/) defines an RBAC reference model and an administrative functional specification. Users are assigned roles; roles carry permissions to act on objects. The [NIST model paper, sections 3 and 7.4](https://tsapps.nist.gov/publication/get_pdf.cfm?pub_id=916402) explicitly leaves the nature of permissions to the application: `read`/`write` and business operations such as `credit`/`debit` are both valid. The model also discusses hierarchies and separation of duties; it does not require applications to copy the same vocabulary. Warehouse-parser's one-role-per-user restriction is a local design choice, not a claim of formal standards conformance.
- **HTTP methods describe requests, not who may perform them.** [RFC 9110, section 9](https://www.rfc-editor.org/rfc/rfc9110.html#section-9) defines method semantics. [Google AIP-121](https://google.aip.dev/121) defines a resource-oriented API convention of `Get`, `List`, `Create`, `Update`, and `Delete`, with custom methods for actions that do not fit. Neither prescribes how to name an authorization grant. A batch query sent as `POST` can still require `read`; an export sent as `GET` can require more than `read`.
- **`resource:action` is a convention, not a standard syntax.** The separator, singular versus plural resource names, whether reads are split, and whether scope is a separate field vary across projects. Keep a consistent convention within the application.

## What Go projects actually use

These are representative public implementations and libraries, not an ecosystem-wide usage survey. They show recurring patterns, not a single Go default.

| Go project | Observed convention | Takeaway |
| --- | --- | --- |
| [Coder](https://github.com/coder/coder/blob/main/coderd/rbac/policy/policy.go) | Typed `Action string` with `create`, `read`, `update`, `delete`, plus `assign`, `unassign`, `start`, `stop`, and `share` | Closest to the warehouse model: typed CRUD plus business actions, with descriptions for each supported resource/action pair. |
| [Kubernetes](https://kubernetes.io/docs/reference/access-authn-authz/authorization/#request-verbs-and-authorization) | `get`, `list`, `watch`, `create`, `update`, `patch`, `delete`, and `deletecollection`; also special actions such as `approve` | Split an action when the distinction is useful to an operator or automation client. `list` and `watch` can expose full resource content, not just metadata. |
| [Grafana Enterprise and Cloud](https://grafana.com/docs/grafana/latest/administration/roles-and-permissions/access-control/custom-role-actions-scopes/) | Actions such as `dashboards:read`, `dashboards:write`, `dashboards:create`, and `dashboards:delete`; scope is specified separately | `read`/`write` is common in practice, but `write` may mean update only or multiple mutations depending on the resource. Document the exact effect. |
| [Argo CD](https://argo-cd.readthedocs.io/en/stable/operator-manual/rbac/#rbac-model-structure) | `get`, `create`, `update`, and `delete`, alongside `sync`, `rollback`, `override`, and `invoke` | Business-specific verbs make meaningful privilege differences visible. The resource, action, and target object are separate policy fields. |
| [Apache Casbin](https://casbin.apache.org/docs/rbac/) | Policies commonly evaluate subject, object, and action (`sub`, `obj`, `act`); examples use `read`, `edit`, or `write` | A Go authorization library supplies an evaluator, not a canonical verb list. The application defines which actions exist and what they imply. |

## Choosing verbs

| Use | Meaning | Warehouse example |
| --- | --- | --- |
| `read` | View or query data. Group list and detail if the intended audience and disclosure are the same. Split off `list` or `watch` only if operators need to grant it separately. | `order:read` covers list and detail, including line items. `logger_session:read` also covers the batch readings query, despite its `POST` transport. |
| `create`, `update`, `delete` | Add a new entity, change an existing one, or remove it. Keep them separate where independent grants matter. Treat `PUT` and `PATCH` alike when they confer the same authority. | `driver:create`, `driver:update`, `driver:delete`. A full run edit and its status/driver patches require `delivery:update`. |
| `write` | One intentional mutation grant for a bundled operation; not an implied superset of all other verbs. Use only when its scope is clear. | `alias:write` is one upsert covering creation and update, not deletion or bulk import. `logger_device:write` covers configuration, reset, format, and LCD changes in this app; those actions also require device read access and a connection. |
| Business verbs | A distinct operation an administrator would grant or revoke on its own. Avoid broad `manage` or `execute` when a precise verb exists. | `delivery:pick`, `sync:trigger`, `item:export`, `alias:import`, `database:clear`, `barcode:print`. `item:export` also requires `item:read`; `alias:import` includes bulk replacement. |

**Choose by effect, not handler name or number of routes.** A picker can mark items without editing the whole run. A supervisor's existing `delivery:update` is broader and can change any state accepted by the full update; describing `delivery:pick` as the only way to change picked state would mislead administrators. Likewise, separate export enables control over the supplied bulk-download feature; it does not make already-readable data impossible to copy. If approval, bulk replacement, or another destructive variant needs a separate operator, split it deliberately and map every path that performs it.

### Current names worth documenting, not renaming now

| Existing keys | Actual authority | Prefer for a new equivalent design |
| --- | --- | --- |
| `user:create`, `user:update` | Approve an existing guest into the default `user` role; reassign an account, respectively. Approval does not create an identity. | `user:approve`, `user:assign_role`. Define whether general assignment can also approve; a different name alone does not enforce that boundary. |
| `accurate:create`, `accurate:update`, `accurate:delete` | Start or complete shared login/OTP, change the shared tenant, or end the shared session. These do not authorize CRUD on Accurate business records. | `accurate:connect`, `accurate:select_tenant`, `accurate:disconnect`. |

Keep existing persisted keys and present precise labels such as **Approve guest** and **Switch shared Accurate tenant** in administrator-facing copy. The last column is illustrative, not a proposed migration. If a future change renames a key, treat it as a contract change across SQLite grants, the API catalog, Go policies and tests, the generated TypeScript union, and both locale dictionaries. A rename must preserve the old authority exactly; a split or expansion needs a separate migration decision and must not silently grant broader access.

## Enforcement practices

1. **Default to no access; check on the server.** Resolve identity separately from authorization and require a declared policy on each operation, including downloads, batch requests and streams. Frontend controls improve usability but are not enforcement. Reject unknown grants and fail closed when authorization data is unavailable. Use explicit all-of and any-of rules rather than assuming that similar verbs imply one another. See the [OWASP Authorization Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html#recommendations).
2. **Use roles as job functions and keep scope separate.** Start from tasks such as Picker or Sync Observer, not a ladder of role names. Explain what a read returns, including embedded records and aggregates. When location, tenancy or ownership becomes a real requirement, combine role capabilities with a target or relationship check and constrain collection queries server-side. Do not create a role for every record or assume endpoint RBAC provides row-level isolation.
3. **Treat role assignment and policy editing as privileged actions.** Check the actor, current target, and proposed authority in the same transaction as the write. A delegate should not grant rights they do not hold or edit the role that gives them power. Kubernetes provides a useful comparison: its normal checks bound role edits and bindings to grants the caller already holds, with explicit `escalate` and `bind` exceptions ([Kubernetes RBAC](https://kubernetes.io/docs/reference/access-authn-authz/rbac/#privilege-escalation-prevention-and-bootstrapping)). Do not add equivalents unless needed. Keep recovery access separate and review its holders; a wildcard can include future capabilities ([Kubernetes RBAC good practices](https://kubernetes.io/docs/concepts/security/rbac-good-practices/#least-privilege)). Warehouse's `*` is an implicit-admin response marker, not an assignable catalog permission.
4. **Give revocation an explicit contract.** Check current grants rather than trusting an old token's role claim. If access must end immediately for new requests, avoid a permission cache without a matching invalidation mechanism. For long-lived streams, check access before delivery and terminate on revocation, expiry, or failed verification. Do not promise to retract data already delivered.
5. **Test the permission matrix and audit privileged changes.** Check allowed and denied outcomes, missing identity, unknown operations, cross-resource data exposure, same-session revocation, and denied writes that leave state unchanged. For operational auditability, record who changed whose role or grants, when, what changed, and the outcome; omit credentials and sensitive payloads. Review access periodically for privilege creep. See [OWASP logging and authorization testing guidance](https://cheatsheetseries.owasp.org/cheatsheets/Authorization_Cheat_Sheet.html#implement-appropriate-logging).

## Practical choice for this repository

Keep the in-process Go implementation while role policy is shared by one application and SQLite transactions own the relevant state. The [permission registry](../pkg/model/permission.go), [API policy declarations](../pkg/api/server.go), and [transactional role administration](../pkg/storage/rbac.go) already provide explicit boundaries. When adding a capability, update the registry, regenerate the TypeScript union with `go generate ./pkg/model`, document its effect in both locales, and add a positive and negative assertion to the [API integration tests](../pkg/api/rbac_test.go). The [API permission reference](../README.md#api--permission-reference) describes the currently shipped grants.

Reconsider the evaluator if multiple services need centrally distributed policy, or when role checks no longer express the required object rules. Casbin can provide a configurable in-process evaluator; [Open Policy Agent](https://www.openpolicyagent.org/docs/integration) supports embedded Go evaluation, a policy SDK, or a separate decision service. Neither replaces the need to define action semantics, query scope, transaction boundaries, or revocation behavior. A preference for different verb names is not a reason to adopt a policy engine.
